# MotionForge vs Remotion

Remotion is excellent when you want to author videos as React components and
render through its server, cloud, or client-side pipelines. MotionForge is
built for a different base-layer contract: the video itself is a validated,
serializable document rather than an executable React program.

## Mental Model

Remotion:

```txt
write React components -> preview in Studio/Player -> render on web, Node, or cloud
```

MotionForge:

```txt
write deterministic scene data -> preview in Studio -> export in browser
```

## Main Differences

| Topic                 | Remotion                                                        | MotionForge                                                   |
| --------------------- | --------------------------------------------------------------- | ------------------------------------------------------------- |
| Authoring unit        | React component program                                         | Serializable scene JSON                                       |
| Validation            | Mostly TypeScript/runtime                                       | Schema + cross-field validation                               |
| Preview               | DOM/React composition                                           | Canvas2D renderer                                             |
| Browser export        | `@remotion/web-renderer` via WebCodecs and Mediabunny           | Canvas2D reference renderer via WebCodecs and Mediabunny      |
| Server/cloud export   | Mature Node, serverless, and distributed options                | Reference frame loop; deployment adapter is application-owned |
| Preview/export parity | DOM preview; server screenshots or client Canvas reconstruction | The same Canvas2D renderer drives preview and export          |
| Agent friendliness    | Agent writes code                                               | Agent writes or patches data                                  |
| Styling               | Web platform breadth                                            | Curated CSS-like subset                                       |
| Storage/diffing       | Source code                                                     | Scene documents and patch ops                                 |

## Browser rendering is not the differentiator

Remotion's client-side renderer is stable from v4.0.491, so browser export by
itself is not a MotionForge moat. Remotion reconstructs a supported subset of
DOM elements and CSS onto Canvas and also supports ecosystem components such
as SVG, Lottie, Rive, Three.js, and Skia. See the official
[client-side rendering overview](https://www.remotion.dev/docs/client-side-rendering)
and [limitations](https://www.remotion.dev/docs/client-side-rendering/limitations).

MotionForge's differentiator is the complete data contract around rendering:
scenes can be validated without executing code, patched transactionally by
node id, migrated, stored, diffed, inspected, and generated by an agent. Its
smaller rendering vocabulary is deliberate, and preview/export equivalence is
straightforward because both paths call the same renderer.

## Why Choose MotionForge

Choose MotionForge when:

- videos are generated or edited by agents
- scenes should be stored as JSON documents
- you need schema validation before rendering
- preview and export should share one renderer
- your product needs preview and export to share one explicit renderer
- you want a constrained visual contract that tools can reason about
- executing arbitrary generated application code is unacceptable
- an MIT engine and portable scene documents matter to the product

Choose Remotion when:

- you want the full React and browser layout model
- arbitrary CSS and DOM composition are more important than data portability
- videos are authored mainly by frontend engineers, not generated as documents
- you need Remotion's existing SVG, Rive, Three.js, Skia, serverless, or
  distributed-rendering ecosystem

## Compatibility Strategy

MotionForge should not imitate every Remotion feature. The strongest path is:

- keep the scene document canonical
- make TypeScript authoring concise
- make Studio fast enough for iteration
- expose validation errors that humans and LLMs can fix
- add adapters only when they compile down to serializable scene data

React/JSX authoring can exist later as an adapter, but it should compile to the
same scene format rather than replacing it. Browser rendering, additional
renderers, and cloud workers should likewise consume that document instead of
creating a second authoring contract.
