# RFC 0009 — Post-1.0 engine platform architecture

- Status: Accepted
- Date: 2026-08-25
- Target milestone: MF0
- Behavior change: None

## Decision

MotionForge remains an independent, deterministic video document engine. Scene
JSON is the canonical low-level render IR; authoring APIs, semantic commands,
macros, JSX adapters, and agent tools compile to or transactionally modify that
IR. Canvas2D remains the reference renderer but is separated from the future
renderer-neutral evaluated layout/display-list contract.

MotionForge owns generic document, evaluation, layout, media/audio, inspection,
mutation, rendering, playback, and export mechanics. It does not own an LLM
provider, autonomous agent, SaaS application, database, queue, billing system,
or product editorial policy.

The detailed public entry-point ownership and deprecation baseline is
[`../public-api-ownership.md`](../public-api-ownership.md). The post-1.0 delivery
order is defined by [`../post-1.0-engine-roadmap.md`](../post-1.0-engine-roadmap.md).

## Canonical layers

```text
authoring helpers / JSX / presets / semantic commands
                         │ compile
                         ▼
               canonical Scene document
                         │ evaluate
                         ▼
          resolved timing + layout + display list
                         │ render
                         ▼
               renderer backend + resources
                         │ orchestrate
                         ▼
                 player / export / tools
```

Only Scene documents are canonical and persistable by engine contract.
Resolved scenes, layouts, display lists, decoded media, workspaces, and runtime
sessions are ephemeral. Hosts may persist command logs or revisions, but those
are not alternative render formats.

## Engine boundary

MotionForge owns:

- Scene schemas, versions, migrations, validation, and low-level patches;
- deterministic frame evaluation, layout, and renderer-neutral paint intent;
- technical asset metadata, generic resource policy, preparation, and disposal;
- audio placement, mixing, automation, analysis, and preview/export adapters;
- generic semantic commands and in-memory revision/workspace mechanics;
- deterministic tree, timeline, layout, audio, and export inspection;
- renderer implementations, player mechanics, and export protocols;
- framework-neutral CLI, skill, MCP, and function-tool adapters.

MotionForge excludes:

- provider/model SDKs, prompts, conversation memory, autonomous planning, and
  token policy;
- ASR, semantic media descriptions, embeddings, retrieval, stock search, and
  generated-media providers;
- accounts, permissions, billing, credits, databases, queues, cloud storage,
  analytics, routes, or product project identifiers;
- product timeline models, editorial policy, selection/UI state, and approval
  workflows;
- executable source, module URLs, callbacks, or remote shaders in Scene data.

Generic host interfaces are allowed for asset resolution, artifacts,
cancellation, progress, fallback rendering, and diagnostics. Implementations of
those interfaces remain host-owned.

## Dependency direction

In the diagrams below, `A -> B` means **A may depend on B**.

The accepted 1.0 dependency graph is recorded mechanically in
`scripts/package-contracts.mjs`. It describes the current implementation and is
not silently rewritten to match the target graph.

The target post-1.0 direction is:

```text
core             -> schema
extensions       -> schema
presets          -> schema (+ core only when pure evaluation types are needed)
inspection       -> schema + core
commands         -> schema + presets
media/audio      -> schema + core as their extracted contracts require

renderer-canvas2d -> schema + core + extensions + media
runtime           -> schema + core + inspection + extensions + media/audio contracts
player            -> runtime + audio
export            -> runtime + audio
authoring         -> schema + core + presets
agent-tools       -> commands + inspection + runtime + export + preset manifests
cli               -> public facades above
```

`runtime` depends on an abstract renderer-session contract. It must not depend
on player or export, and the abstract contract must not depend on Canvas2D.
Concrete convenience factories may assemble runtime with Canvas2D in an adapter
entry point without reversing the base dependency.

New packages are not created merely to shorten files. Media/audio become public
packages only when their extracted interfaces are independently useful and the
old import locations have compatibility re-exports.

## Enforced package rules

`pnpm check:contracts` enforces the current graph and public entry points:

1. every public package has an owner and an allowed internal dependency list;
2. public packages use `workspace:*` for MotionForge dependencies;
3. a public package cannot depend on a private workspace package;
4. public package dependency cycles fail;
5. source imports must use declared, exported package entry points;
6. relative imports cannot escape a public package directory;
7. product aliases, application frameworks, auth/database/billing clients,
   model SDKs, and agent frameworks cannot enter engine package sources;
8. public package exports/bins match the committed API baseline.

Changing an allowed dependency or public entry point requires an architecture
review and matching baseline/documentation update. A controlled Node test suite
proves that forbidden edges/imports and cycles are rejected without committing
an invalid fixture into package source.

## Public packages and entry points

All package `exports` entry points are stable for 1.x. Symbols exported through
those entry points are public even when documentation is incomplete. MF0
machine-checks package entry points and bins; it does not claim a declaration
or symbol-level API report. Renderer/media resource shapes documented as
advanced may grow additively, while lifecycle entry points and documented
ordering remain stable. Future extraction moves implementation ownership while
compatibility re-exports preserve existing imports.

No existing 1.0 entry point is deprecated by this RFC.

## Compatibility and migration

1. Scene v1 remains canonical for the 1.x line.
2. Existing timing/default/pixel semantics do not change silently.
3. Breaking document changes require a new Scene version and migration.
4. Breaking package API changes require a package major version.
5. Moved APIs retain their old import as a compatibility re-export through 1.x.
6. Exact-pixel renderer fixes require changelog notes and reviewed goldens.
7. A future display list is ephemeral; it is not a Scene replacement or storage
   compatibility promise.

## Downstream synchronization

The MotionForge repository is authoritative for reusable engine behavior.
Downstream applications consume an exact published version or exact upstream
commit. Each upgrade is a separate downstream commit with recorded provenance
and its own consumer test matrix.

Generally reusable fixes land upstream first. Product adapters stay downstream.
Temporary downstream emergency fixes must be reconciled upstream immediately;
an unrecorded source copy under the same package identity is prohibited.

MotionForge retains old Scene readers and compatibility exports until persisted
downstream projects and imports have a tested migration path.

## Alternatives rejected

### Make React or HTML the canonical video

Rejected because executable application code cannot provide the same bounded
validation, migration, transactional patching, or safe multi-tenant artifact.
React/JSX remains an optional compiler into Scene data.

### Treat Canvas2D as the permanent engine boundary

Rejected because layout, inspection, resource preparation, and display intent
must be reusable by future renderer backends. Canvas2D remains the conformance
backend rather than the canonical document.

### Put an autonomous agent in the engine

Rejected because model choice, planning, cost, memory, approval, and product
policy belong to hosts. MotionForge exposes deterministic, provider-neutral
tools that an agent may use.

### Split every subsystem into a public package immediately

Rejected because package count is an API and maintenance cost. Extraction must
first establish a coherent owner, independent contract, compatibility facade,
and clean-install use case.

## MF0 evidence

MF0 changes architecture documentation and enforcement only. It performs no
package move, Scene change, renderer change, or pixel change.

Required evidence:

```sh
pnpm check:contracts
pnpm release:fast
```

The release gate demonstrates that the stronger boundary checks do not alter
current engine behavior.
