# Migrating from the 1.0 source baseline to the 1.1 candidate

Status: 1.1.0 release-candidate guidance

The repository's 1.0.0 manifests and changelog define a stable source/API
baseline, but this checkout has no verifiable 1.0 Git tag or npm publication
receipt. This guide therefore covers projects consuming an exact 1.0 commit,
workspace override, vendored snapshot, or locally packed 1.0 tarballs. It does
not claim that an external `@dojo-video-engine/*@1.0.0` release exists.

Do not install the public npm package named `create-dojo-video-engine`; that name is
owned by an unrelated project. Dojo Video Engine 1.1 uses the package identity
`@dojo-video-engine/create` and retains `create-dojo-video-engine` only as its executable
name.

## Compatibility summary

- Canonical stored documents remain Scene v1. There is no Scene v1 → v2 data
  migration in 1.1.
- Existing 1.0 root imports and Scene defaults remain governed by the 1.x
  compatibility policy.
- Public APIs added by the post-1.0 milestones are additive packages or entry
  points. Consumers opt into them.
- Renderer fixes that intentionally change pixels are identified in the 1.1
  changelog and golden evidence; validate important compositions before
  rollout.
- Legacy extension renderer adapters remain supported for all of 1.x. New
  standard/opaque display contracts are opt-in.
- Legacy stateless agent tools remain available. The handle-based iterative
  workflow is additive and does not require a model SDK.

Read [`../compatibility.md`](../compatibility.md),
[`../extension-abi.md`](../extension-abi.md), and the final 1.1 changelog before
upgrading.

## Package upgrade

Dojo Video Engine public packages version together. Upgrade every Dojo Video Engine package
used by one application to the same verified 1.1.x version; do not mix a 1.0
workspace snapshot with 1.1 runtime/renderer/schema packages.

Before external 1.1 publication, consume an exact reviewed commit through a
workspace or package-manager override, or use tarballs produced by `pnpm pack`
from that commit. After publication is verified under
[`../release-process.md`](../release-process.md), replace those overrides with
the exact registry version and commit the lockfile change.

If the project invokes the starter generator, change the package identity:

```diff
- "create-dojo-video-engine": "<old local source>"
+ "@dojo-video-engine/create": "1.1.0"
```

The command remains `create-dojo-video-engine`. For one-off execution after a
verified external release, use the scoped package explicitly rather than
`pnpm create dojo-video-engine` so the unrelated unscoped package cannot be selected:

```sh
pnpm dlx @dojo-video-engine/create@1.1.0 my-video
```

Do not run that registry command until `@dojo-video-engine/create@1.1.0` publication
and provenance have been verified.

## Scene storage and Layout v2

Keep canonical Scene v1 as the stored render document. Layout v2 is an
authoring plan that compiles deterministically to an absolute-pixel Scene v1
projection. Retain both the source Scene and `LayoutPlan` when future reflow or
agent editing matters; do not persist the compiled projection as the only
authoring source.

Layout text planning may project resolved direction, physical alignment,
font, size, line height, explicit line breaks, and ellipsis into Scene v1 so
the renderer reproduces the plan. That projected text is output, not a safe
replacement for the original authoring text/metrics evidence.

Existing Scene v1 documents need no layout conversion. Adopt
`@dojo-video-engine/layout` only for compositions that benefit from stack, grid,
overlay, constraints, safe areas, or deterministic intrinsic planning.

## Runtime and renderer

Prepared revisioned rendering is available through `@dojo-video-engine/runtime` and
`@dojo-video-engine/renderer-canvas2d/runtime`. Existing Canvas2D entry points remain
valid. When adopting the prepared runtime:

- treat prepared revisions, display lists, caches, and artifact handles as
  ephemeral;
- pass expected revisions for mutations and join asynchronous disposal;
- supply explicit asset/network credential policy in the host;
- preserve browser capability preflight and a documented export fallback.

Do not store prepared runtime objects or decoded media in Scene JSON.

## Extensions

No extension descriptor is silently upgraded. Keep each stored exact
`{name, version, params}` until a tested project migration changes it.

Existing definitions with `renderers` continue through the exact legacy bridge.
New definitions should choose either standard display v1 or one exact opaque
capability. A definition cannot expose both a new display contract and legacy
renderer adapters. Re-test worker declarations, cancellation, resource
disposal, output bounds, and compatibility aliases under the
[extension ABI](../extension-abi.md).

## Commands and agent workflows

`@dojo-video-engine/commands` adds strict non-recursive command schemas, reversible
patch compilation, and revisioned workspaces. `@dojo-video-engine/agent-tools` adds a
session-scoped handle workflow with inspect/search/check/command/undo/redo and
evidence seams. Adoption is optional:

1. load a recursive Scene only at the strict workspace boundary;
2. expose opaque handles and bounded flat results to the model;
3. use expected revisions and reject stale writes;
4. authorize host-owned assets before applying `asset.set`;
5. run deterministic checks/render evidence and repair loops;
6. retrieve the final Scene/history through the host-only snapshot API;
7. dispose handles/session resources.

Do not pass the complete Scene back on each model turn, accept raw model patches
without command validation, or let a model invent media URLs. Existing one-shot
tool integrations can migrate incrementally; no provider framework is required.

## Verification checklist

For a downstream application:

- remove any unscoped `create-dojo-video-engine` dependency or invocation;
- update all consumed Dojo Video Engine packages/overrides together and refresh the
  lockfile;
- validate every stored Scene and run migration idempotence checks;
- run unit tests plus representative preview/export/browser tests;
- compare critical compositions against saved 1.0 pixels/audio/timing;
- exercise extension preflight and missing-version/capability failures;
- verify media credential/source policy and worker/runtime disposal;
- if adopting workflow tools, test stale revisions, rollback, invented assets,
  bounded results, abort, and cleanup;
- pin the verified candidate commit or externally published package integrity.

In this repository, the corresponding candidate gates are:

```sh
pnpm check:contracts
pnpm check:schema
pnpm check:migrations
pnpm release:full
pnpm verify:clean
```

## Rollback

Keep the pre-upgrade lockfile, exact 1.0 source commit/tarballs, source Scenes,
LayoutPlans, and project history until production validation completes. Roll
back the dependency/override commit as one unit. Do not attempt to downgrade a
Scene by deleting unknown fields; use only a documented deterministic migration
or restore the retained source document.

Report compatibility defects with a minimal Scene, exact before/after commits
or package integrities, browser/Node versions, assets/fonts/extension versions,
and expected versus actual output. Security-sensitive defects follow
[`../../SECURITY.md`](../../SECURITY.md).
